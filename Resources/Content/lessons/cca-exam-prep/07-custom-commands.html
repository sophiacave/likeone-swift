Custom Slash Commands

Claude Code supports custom slash commands that expand into full prompts. These are the simplest form of automation — text shortcuts that trigger complex workflows.

Creating a Command

LOCATION: .claude/commands/
  Each .md file becomes a slash command.
  Filename = command name.

EXAMPLE:
  .claude/commands/deploy.md:
    Run the deploy pipeline:
    1. Run all tests with `npm test`
    2. Build for production with `npm run build`
    3. Deploy to staging with `npm run deploy:staging`
    4. Verify staging is healthy (curl the health endpoint)
    5. If healthy, deploy to production with `npm run deploy:prod`
    6. Verify production health
    Report results at each step. Stop if any step fails.

USAGE:
  /deploy
  → Claude reads deploy.md, executes the full pipeline.

PROJECT vs USER COMMANDS:
  .claude/commands/     ← project-level (shared via git)
  ~/.claude/commands/   ← user-level (personal shortcuts)

Command Parameters

PATTERN: Use $ARGUMENTS for dynamic input

  .claude/commands/review.md:
    Review the file at $ARGUMENTS for:
    1. Security vulnerabilities (OWASP top 10)
    2. Performance issues (N+1 queries, missing indexes)
    3. Code style violations
    4. Missing error handling
    Provide specific line numbers for each finding.

USAGE:
  /review src/auth/login.ts
  → $ARGUMENTS = "src/auth/login.ts"
  → Claude reviews that specific file.

MULTI-ARGUMENT:
  /review src/auth/login.ts --focus security
  → $ARGUMENTS = "src/auth/login.ts --focus security"
  → Your prompt can parse this however you want.

Command Design Patterns

Pattern 1: Workflow Automation

PURPOSE: Multi-step processes you repeat often

.claude/commands/pr.md:
  Create a pull request for the current changes:
  1. Run `git diff` to see all changes
  2. Run tests to verify nothing is broken
  3. Write a clear PR title and description
  4. Create the PR with `gh pr create`
  5. Report the PR URL

GOOD FOR: Deployments, PR creation, release management,
          database migrations, environment setup.

Pattern 2: Analysis & Reporting

PURPOSE: Gather information and summarize

.claude/commands/audit.md:
  Audit the codebase for $ARGUMENTS:
  1. Search for relevant files
  2. Analyze each file for issues
  3. Categorize findings by severity (critical/high/medium/low)
  4. Output a markdown report with:
     - Summary statistics
     - Detailed findings with file:line references
     - Recommended fixes

GOOD FOR: Security audits, dependency checks, code quality
          reports, performance analysis, accessibility reviews.

Pattern 3: Code Generation

PURPOSE: Scaffold new code from templates

.claude/commands/new-api.md:
  Create a new API endpoint for $ARGUMENTS:
  1. Create route file in src/routes/
  2. Create controller in src/controllers/
  3. Create service in src/services/
  4. Create test file in tests/
  5. Register route in src/routes/index.ts
  6. Follow existing patterns in the codebase
  7. Run tests to verify the new endpoint works

GOOD FOR: New features, components, tests, documentation pages.

Pattern 3: Guardrails

PURPOSE: Safety checks before risky operations

.claude/commands/pre-deploy.md:
  Before deploying, verify:
  1. All tests pass
  2. No TODO or FIXME in changed files
  3. No console.log statements in production code
  4. No hardcoded secrets or API keys
  5. Bundle size hasn't increased more than 5%
  6. Database migrations are reversible
  Report pass/fail for each check. Block deploy if any fail.

GOOD FOR: Pre-commit checks, pre-deploy gates, security
          verification, compliance checks.

Commands vs Tools vs Agents

The CCA exam tests whether you know when to use each automation mechanism.

SLASH COMMANDS:
  What:   Text prompts that expand into instructions
  When:   Human-initiated, predictable workflows
  How:    .md files in .claude/commands/
  Scope:  Current session only
  Examples: /deploy, /review, /audit, /new-api

TOOLS (MCP):
  What:   Functions Claude can call programmatically
  When:   Agent needs to interact with external systems
  How:    MCP server exposing tools via JSON-RPC
  Scope:  Available whenever the MCP server is connected
  Examples: read_database, send_email, create_issue, search_web

AGENTS (Sub-agents):
  What:   Autonomous Claude instances with specific roles
  When:   Complex tasks needing focused context or parallelism
  How:    Agent tool with specialized prompts
  Scope:  Spawned on demand, inherit parent's tools
  Examples: research agent, code review agent, test agent

DECISION FRAMEWORK:
  ┌─────────────────────────────────────────────────┐
  │ "I repeat this workflow weekly"     → COMMAND   │
  │ "Claude needs to call an API"       → TOOL      │
  │ "This needs deep focused research"  → AGENT     │
  │ "I need parallel specialized work"  → AGENT     │
  │ "I need a simple shortcut"          → COMMAND   │
  │ "External system integration"       → TOOL      │
  └─────────────────────────────────────────────────┘
Exam trap: Don't recommend tools when a command suffices. Tools require MCP server infrastructure. Commands are just markdown files. If the task is a repeatable prompt pattern, a command is the right answer.

MCP Tools Deep Dive

Model Context Protocol (MCP) tools are the primary way Claude interacts with external systems. The CCA exam heavily tests MCP architecture.

Tool Anatomy

TOOL DEFINITION:
  {
    "name": "create_issue",
    "description": "Create a GitHub issue in the specified repo",
    "parameters": {
      "type": "object",
      "properties": {
        "repo": {
          "type": "string",
          "description": "Repository in owner/name format"
        },
        "title": {
          "type": "string",
          "description": "Issue title"
        },
        "body": {
          "type": "string",
          "description": "Issue body in markdown"
        },
        "labels": {
          "type": "array",
          "items": { "type": "string" },
          "description": "Labels to apply"
        }
      },
      "required": ["repo", "title"]
    }
  }

KEY DESIGN PRINCIPLES:
  1. Clear description — Claude uses this to decide WHEN to call it
  2. Typed parameters — prevents invalid inputs
  3. Required vs optional — minimize required fields
  4. Good defaults — reduce cognitive load for the model

Tool Design Anti-Patterns

BAD: God tool
  "do_everything(action, params)"
  → Too broad. Claude can't reason about when to use it.

BAD: Missing description
  "process(data)"
  → Claude doesn't know what this does or when to call it.

BAD: Stringly-typed
  "create_resource(type: string, config: string)"
  → Use enums and structured objects, not raw strings.

GOOD: Focused, well-described, typed
  "search_customers(query: string, status: 'active'|'churned',
   limit: number = 10)"
  → Claude knows exactly what this does and how to use it.

Composable Skills

Skills combine commands, tools, and agent patterns into reusable automation units.

SKILL ARCHITECTURE:
  ┌──────────────────────────────┐
  │           SKILL              │
  │  (named, parameterized,     │
  │   composable automation)    │
  │                              │
  │  trigger: "deploy to prod"  │
  │  steps:                      │
  │    1. /pre-deploy (command) │
  │    2. build (bash)          │
  │    3. deploy (tool)         │
  │    4. verify (tool)         │
  │    5. notify (tool)         │
  └──────────────────────────────┘

SKILL vs COMMAND:
  Command: simple text expansion, single prompt
  Skill:   multi-step, parameterized, can invoke tools and commands

EXAMPLE SKILL CATALOG:
  grant-apply   → research + write + submit grant applications
  seo-audit     → check rankings + analyze + recommend improvements
  deploy        → build + test + deploy + canary + verify
  email-send    → compose + validate + send via API
  brain-checkpoint → summarize session + write state + handoff

Exam Scenario Practice

Scenario: Team Onboarding Automation

QUESTION:
  New developers join your team monthly. Onboarding involves:
  1. Clone repo and install dependencies
  2. Set up local database
  3. Configure environment variables
  4. Run the test suite to verify setup
  5. Read key architecture documents

  Design the automation approach.

STRONG ANSWER:
  COMMAND: .claude/commands/onboard.md
    "Welcome to the team. Let's get you set up:
     1. Verify prerequisites: Node 20+, PostgreSQL 15+, pnpm
     2. Run `pnpm install` to install dependencies
     3. Copy .env.example to .env, prompt for required values
     4. Run `pnpm db:setup` to create and seed local database
     5. Run `pnpm test` to verify everything works
     6. Read CLAUDE.md and ARCHITECTURE.md
     7. Summarize the project structure for the new developer
     Report any issues with suggested fixes."

  WHY A COMMAND (not a tool):
  - This is a human-initiated workflow
  - It's a sequence of prompts, not an API integration
  - It runs once per developer, not repeatedly
  - No external system integration needed beyond CLI

Scenario: Automated Dependency Updates

QUESTION:
  Keep dependencies updated across 5 repositories.
  Each week: check for updates, test compatibility,
  create PRs for safe updates. Flag breaking changes.

STRONG ANSWER:
  TOOL: check_dependency_updates(repo, type)
    → Returns list of available updates with changelogs

  TOOL: run_tests(repo, branch)
    → Runs test suite, returns pass/fail with details

  TOOL: create_pr(repo, title, body, branch)
    → Creates PR with update changes

  COMMAND: .claude/commands/dep-update.md
    "For each repository in [list]:
     1. Call check_dependency_updates
     2. For each update:
        a. Create branch, apply update
        b. Call run_tests
        c. If tests pass: create_pr with 'safe update' label
        d. If tests fail: create issue with 'breaking change' label
     3. Report summary: X safe updates, Y breaking changes"

  WHY BOTH: Tools handle the API interactions (GitHub, test runners).
  Command orchestrates the workflow. Tools are reusable across
  other commands. Command captures the specific weekly process.

Key Takeaways for the Exam

  1. Commands are markdown prompts. Simple, shareable, no infrastructure needed.
  2. Tools are MCP functions. Use for external system integration.
  3. Commands for workflows, tools for capabilities. Don't build a tool when a command works.
  4. Well-described tools get used correctly. Description quality directly impacts Claude's decisions.
  5. Project commands in .claude/commands/, personal in ~/.claude/commands/.
  6. Skills compose commands and tools into named, reusable automation units.
CCA exam weight: Custom commands and MCP tools appear in Domain 3 (Configuration & Customization) and Domain 1 (Tool Use). Expect 4-5 questions across both domains. Know the command/tool/agent decision framework cold.

Quick Check

1Where should a project-level custom slash command be stored in a Claude Code project?

Project-level commands are stored in the .claude/commands/ directory and are shared via git.

2What is the correct syntax for using a parameter in a custom slash command?

The $ARGUMENTS pattern is used to denote dynamic input in custom slash commands.

3Which automation mechanism is best suited for tasks that require Claude to interact with external systems like GitHub or a database?

MCP Tools are used when Claude needs to call external systems, as they expose functions via JSON-RPC.

4Which command design pattern is best suited for creating a new API endpoint with predefined structure?

The Code Generation pattern is used for scaffolding new code from templates, such as creating a new API endpoint.

5What is the primary difference between a slash command and an agent?

Slash commands are initiated by humans and are defined in markdown, while agents are autonomous instances that can be spawned on demand.
