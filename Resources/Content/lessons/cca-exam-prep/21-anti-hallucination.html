The Five Hallucination Categories

1. FACTUAL HALLUCINATION
   Agent states something false as fact.
   "Python 3.12 removed list comprehensions" (it didn't)
   CAUSE: Model generating plausible-sounding but wrong info.

2. FABRICATED REFERENCES
   Agent cites non-existent sources.
   "According to RFC 9847..." (doesn't exist)
   CAUSE: Model pattern-matches citation format without verifying.

3. INVENTED DATA
   Agent creates fake statistics or numbers.
   "Our uptime was 99.97% last month" (never measured)
   CAUSE: Model fills in numbers when none are available.

4. CAPABILITY HALLUCINATION
   Agent claims to have done something it didn't.
   "I've deployed the fix to production" (no deploy tool exists)
   CAUSE: Model generates expected success narrative.

5. CONTEXT HALLUCINATION
   Agent attributes information to the wrong source.
   "As mentioned in the PR description..." (PR says no such thing)
   CAUSE: Model confuses or fabricates context linkages.

Grounding Strategies

Strategy 1: Source Grounding

RULE: Every claim must have a source.

SYSTEM PROMPT INSTRUCTION:
  "When stating facts, cite the source.
   If you don't have a source, say 'I don't have data on this.'
   Never invent statistics, dates, or measurements.
   Acceptable sources: tool results, file contents, user-provided data.
   Unacceptable: your training data for specific numbers."

EXAMPLE:
  BAD:  "The API handles 10,000 requests per second."
  GOOD: "According to the load test results in tests/bench.json,
         the API handled 8,432 requests per second at p95."
  BEST: "I don't have load test data. Run the benchmark
         with 'npm run bench' to get current numbers."

Strategy 2: Tool-First Architecture

PRINCIPLE: Use tools to verify instead of generating from memory.

BAD FLOW:
  User: "What's our current user count?"
  Agent: "Based on our growth trends, approximately 15,000 users."
  → Hallucinated number. No tool call made.

GOOD FLOW:
  User: "What's our current user count?"
  Agent: calls count_users() → returns 12,847
  Agent: "There are 12,847 registered users as of right now."
  → Real number from actual database query.

SYSTEM PROMPT FOR THIS:
  "For any question about current state (counts, status, metrics),
   ALWAYS use a tool to get the real data.
   Never estimate, predict, or guess from context.
   If no tool exists for the data, say so."

Strategy 3: Uncertainty Expression

CALIBRATED CONFIDENCE:
  Instead of stating everything as fact:

  HIGH CONFIDENCE (from tool results):
    "The build failed with exit code 1."
    → Directly observed. No uncertainty needed.

  MEDIUM CONFIDENCE (from context):
    "This is likely caused by the recent dependency update,
     based on the timing of the error and the changelog."
    → Inference, not certainty. Qualified with "likely."

  LOW CONFIDENCE (from training data):
    "I believe this pattern is called the saga pattern,
     but I'd recommend verifying in the documentation."
    → Model knowledge, explicitly flagged as uncertain.

  NO CONFIDENCE (no data available):
    "I don't have information about the production error rate.
     Check the monitoring dashboard or run the health check."
    → Honest about gaps. Points to where data exists.

Verification Patterns

PATTERN 1: READ-BEFORE-CLAIM
  Before stating anything about code:
    1. Read the actual file
    2. Find the specific line
    3. Then make the claim with a reference

  "The validateEmail function at auth.ts:42 uses a regex
   that doesn't handle plus-addressing (user+tag@domain.com)."
  → File:line reference. Verifiable. Not hallucinated.

PATTERN 2: CROSS-REFERENCE
  Before stating a fact, check two sources:
    1. Primary source (e.g., database query)
    2. Secondary source (e.g., config file)

  If they disagree → flag the discrepancy.
  If they agree → higher confidence.

PATTERN 3: OUTPUT REVIEW
  After generating a response, review it:
    "Does my response contain any numbers I didn't
     get from a tool call or file read?
     If yes, either verify them or remove them."

  This self-check catches fabricated stats.

PATTERN 4: CLAIM TAGGING
  Tag each claim with its source:
    "Build time: 3.2 seconds [from build output]"
    "Coverage: 87% [from coverage report]"
    "Users affected: unknown [no monitoring data available]"

  Makes it easy to audit which claims are grounded.

Production Anti-Hallucination Architecture

FIVE-LAYER DEFENSE:

  LAYER 1: PROMPT DESIGN
    System prompt with explicit anti-hallucination rules.
    "Never invent data. Always verify. Say 'I don't know.'"

  LAYER 2: TOOL-FIRST WORKFLOW
    Agent reaches for tools before generating answers.
    Tools return real data. Agent reports real data.

  LAYER 3: OUTPUT VALIDATION
    Post-generation check:
    - Does the output contain numbers not from tools?
    - Does it cite sources that don't exist?
    - Does it claim actions that weren't taken?
    If any flag: retry with correction or human review.

  LAYER 4: HUMAN REVIEW
    For high-stakes outputs (legal, financial, medical):
    Human reviews before publication/action.
    Agent flags low-confidence claims for attention.

  LAYER 5: MONITORING
    Track hallucination rate over time.
    Log claims and their sources.
    Automated spot-checks: verify random claims weekly.
    Alert if hallucination rate increases.

EXAM APPLICATION:
  When asked "how do you prevent hallucination?"
  → Don't just say "tell it not to hallucinate."
  → Describe the layered defense. Each layer catches
     what the previous one misses.

Exam Scenario Practice

Scenario: Financial Reporting Agent

QUESTION:
  An agent generates quarterly financial reports.
  It must pull data from multiple sources and present
  accurate numbers. A wrong number could violate SEC
  reporting requirements. Design anti-hallucination.

STRONG ANSWER:
  DATA SOURCING:
    Every number comes from a verified tool call.
    revenue = call stripe_api.get_revenue(q2_2026)
    expenses = call quickbooks_api.get_expenses(q2_2026)
    users = call database.count_users(as_of="2026-06-30")

    NO number is generated from model knowledge.
    If a tool call fails → report "data unavailable" (not a guess).

  CROSS-VERIFICATION:
    Revenue from Stripe must match revenue in QuickBooks.
    If discrepancy > 1%: flag for human review.
    Do NOT average or reconcile automatically.

  OUTPUT FORMAT:
    Each number includes source and timestamp:
    "Revenue: $1,234,567 (source: Stripe API, as of 2026-07-01 10:00 UTC)"
    "Users: 12,847 (source: production database, as of 2026-07-01 10:05 UTC)"

  HUMAN GATE:
    Report is generated as DRAFT.
    CFO reviews and approves before filing.
    Agent cannot submit to SEC directly.

  AUDIT TRAIL:
    Every data point logged: source, timestamp, raw value.
    Report version history maintained.
    Any manual adjustment flagged and explained.

WEAK ANSWER: "Tell the agent to be accurate"
  → No tool-first architecture
  → No cross-verification
  → No human review gate
  → No audit trail

Key Takeaways for the Exam

  1. Five hallucination types. Know them: factual, references, data, capability, context.
  2. Tool-first architecture. Real data from tools beats model-generated guesses.
  3. Say "I don't know." Honest uncertainty is better than confident hallucination.
  4. Layered defense. Prompt + tools + validation + human review + monitoring.
  5. Source every claim. If you can't cite where a number came from, don't use it.
  6. High-stakes = human gate. Never let agents auto-publish financial, legal, or medical content.
CCA exam weight: Anti-hallucination appears in Domain 5 (Security & Safety). Expect 2-3 questions. The exam distinguishes between "tell it to be accurate" (weak) and "design systems that prevent inaccuracy" (strong).
