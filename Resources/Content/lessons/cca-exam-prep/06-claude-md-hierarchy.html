The Configuration Hierarchy

Claude Code loads instructions from multiple sources in a specific order. Understanding this hierarchy is essential for the CCA exam and for production use.

LOADING ORDER (highest to lowest priority):

  1. SYSTEM PROMPT (Anthropic's built-in instructions)
     → You cannot modify this. It defines Claude's core behavior.
     → Sets safety guidelines, tool usage rules, output format.

  2. ENTERPRISE POLICY (org-level, if configured)
     → Set by organization administrators
     → Applies to all projects in the org
     → Cannot be overridden by project-level files

  3. ~/.claude/rules/*.md (USER-LEVEL)
     → Your personal global instructions
     → Apply to ALL projects on your machine
     → Good for: personal preferences, workflow habits
     → Example: "Always use TypeScript" or "Never auto-commit"

  4. CLAUDE.md (PROJECT ROOT)
     → Checked into git. Shared with team.
     → The primary configuration file for any project.
     → Good for: coding standards, architecture decisions,
                  build commands, test instructions

  5. CLAUDE.md (SUBDIRECTORY)
     → Scoped to that directory and its children
     → Overrides or extends parent CLAUDE.md
     → Good for: package-specific rules in a monorepo

  6. .claude/rules/*.md (PROJECT-LEVEL)
     → Additional rules files for the project
     → Same scope as project root CLAUDE.md
     → Good for: separating concerns (deploy.md, testing.md)

  7. SESSION CONTEXT (loaded at runtime)
     → Memory files, RAG results, tool output
     → Most dynamic, least persistent
Exam key point: Higher-priority sources override lower ones. Enterprise policy beats CLAUDE.md. CLAUDE.md beats session context. But they COMBINE — a subdirectory CLAUDE.md doesn't replace the root one, it adds to it.

What Belongs Where

In CLAUDE.md (project root)

INCLUDE:
  ✓ Build and test commands
  ✓ Architecture decisions ("we use PostgreSQL, not MySQL")
  ✓ Coding conventions ("use snake_case for Python files")
  ✓ File structure explanation
  ✓ Common workflows ("to deploy: run X then Y")
  ✓ Important constraints ("never modify the auth module directly")
  ✓ Team-specific patterns ("all API routes go in src/routes/")

DO NOT INCLUDE:
  ✗ Secrets or API keys (use environment variables)
  ✗ Personal preferences (use ~/.claude/rules/)
  ✗ Temporary tasks (use session context)
  ✗ Verbose documentation (link to docs instead)
  ✗ Auto-generated content that changes frequently

In ~/.claude/rules/ (user-level)

INCLUDE:
  ✓ Your editor preferences ("always use 2-space indent")
  ✓ Communication style ("be concise, no emojis")
  ✓ Tool preferences ("use bun instead of npm")
  ✓ Safety rules ("never push without asking")
  ✓ Workflow patterns ("always run tests before committing")

DO NOT INCLUDE:
  ✗ Project-specific rules (those go in CLAUDE.md)
  ✗ Team conventions (those should be shared via CLAUDE.md)
  ✗ Sensitive personal data

In subdirectory CLAUDE.md

USE FOR MONOREPOS:
  /
  ├── CLAUDE.md              ← shared rules (linting, git flow)
  ├── packages/
  │   ├── frontend/
  │   │   └── CLAUDE.md      ← "use React, Tailwind, Vitest"
  │   ├── backend/
  │   │   └── CLAUDE.md      ← "use Express, PostgreSQL, Jest"
  │   └── mobile/
  │       └── CLAUDE.md      ← "use React Native, Expo"

Each subdirectory CLAUDE.md adds context specific to that package
without cluttering the root file with irrelevant details.

Writing Effective CLAUDE.md

Structure Template

# Project Name

## Quick Start
- Build: `npm run build`
- Test: `npm test`
- Deploy: `npm run deploy:staging`

## Architecture
- Framework: Next.js 14 with App Router
- Database: PostgreSQL via Prisma
- Auth: NextAuth.js with Google OAuth
- Hosting: Vercel

## Conventions
- Use server components by default
- Client components only when needed (useState, useEffect)
- API routes in app/api/ follow RESTful naming
- All database queries go through Prisma client in lib/db.ts

## Important Constraints
- NEVER modify prisma/schema.prisma without creating a migration
- NEVER commit .env files
- Always run `npx prisma generate` after schema changes
- The /auth routes are security-critical — extra review required

Anti-Patterns

BAD: Too vague
  "Follow best practices and write clean code"
  → Claude already does this. This adds no information.

BAD: Too verbose
  (500 lines of documentation pasted into CLAUDE.md)
  → Burns context window tokens. Link to docs instead.

BAD: Contradictory rules
  Root: "Always use Jest for testing"
  Subdir: "Always use Vitest for testing"
  → Claude will be confused. Subdirectory should explicitly
     say "Override: use Vitest instead of Jest for this package"

BAD: Stale instructions
  "Deploy to Heroku using git push heroku main"
  (but you migrated to Vercel 6 months ago)
  → Stale CLAUDE.md causes wrong actions. Review quarterly.

GOOD: Specific, current, actionable
  "Run `npm test -- --coverage` before any PR.
   Coverage must stay above 80%. Check with `npm run coverage:check`."

Configuration for Teams

When multiple developers share a project, CLAUDE.md becomes the single source of truth for how Claude should behave in that codebase.

Team Configuration Strategy

LAYER 1 — Organization (enterprise policy)
  "All code must pass security scan before commit"
  "Never use eval() or exec()"
  "All API endpoints require authentication"
  → Enforced by admins. Developers cannot override.

LAYER 2 — Project (CLAUDE.md in repo)
  "This project uses TypeScript strict mode"
  "Database: PostgreSQL 15"
  "CI: GitHub Actions, must pass before merge"
  → Shared via git. All team members see same rules.

LAYER 3 — Personal (~/. claude/rules/)
  "I prefer verbose git commit messages"
  "Always explain your reasoning"
  → Individual preferences. Not shared with team.

Conflict Resolution

QUESTION: What happens when rules conflict?

  User rule:     "Use tabs for indentation"
  Project rule:  "Use 2-space indentation"

ANSWER: Project rule wins for project files.
  Project CLAUDE.md is more specific to the context.
  User rules are defaults that project rules can override.

EXCEPTION: Enterprise policy always wins over everything.
  If org policy says "no tabs", nothing can override that.

EXAM TIP: The hierarchy is:
  Enterprise > Project CLAUDE.md > User rules > Defaults
  More specific context wins over more general context.

Advanced: Dynamic Configuration

Conditional Instructions

PATTERN: Different rules for different situations

  # CLAUDE.md

  ## For bug fixes
  - Always write a regression test BEFORE fixing the bug
  - Reference the issue number in the commit message

  ## For new features
  - Create a design doc before implementation
  - Add feature flag for gradual rollout

  ## For refactoring
  - No behavior changes — tests must pass unchanged
  - Commit in small, reviewable chunks

Claude reads all sections but applies the relevant one
based on the task context.

Environment-Aware Configuration

PATTERN: Rules that reference environment

  # CLAUDE.md

  ## Environment Setup
  - Dev database: localhost:5432/myapp_dev
  - Test database: localhost:5432/myapp_test
  - NEVER connect to production database directly

  ## Deploy
  - Staging: `npm run deploy:staging` (safe to run anytime)
  - Production: `npm run deploy:prod` (REQUIRES explicit approval)

  ## Secrets
  - All secrets in .env (gitignored)
  - Required vars: DATABASE_URL, STRIPE_KEY, JWT_SECRET
  - For local dev: copy .env.example to .env

Exam Scenario Practice

Scenario: Monorepo Configuration

QUESTION:
  You manage a monorepo with 3 packages:
    - web (Next.js frontend)
    - api (Express backend)
    - shared (common types and utilities)

  Each package has different testing frameworks, build tools,
  and deployment targets. How do you configure CLAUDE.md?

STRONG ANSWER:
  Root CLAUDE.md:
    - Shared conventions (TypeScript, ESLint config, git flow)
    - Monorepo tooling (pnpm workspaces, turborepo)
    - "Run `pnpm install` from root, not individual packages"
    - "All packages must export types from shared/"

  packages/web/CLAUDE.md:
    - "Framework: Next.js 14 with App Router"
    - "Test: Vitest + React Testing Library"
    - "Deploy: Vercel (auto-deploys from main)"

  packages/api/CLAUDE.md:
    - "Framework: Express with TypeScript"
    - "Test: Jest + Supertest"
    - "Deploy: Docker → AWS ECS"
    - "Database migrations: `pnpm run migrate`"

  packages/shared/CLAUDE.md:
    - "This package is imported by web and api"
    - "Changes here affect both consumers — run all tests"
    - "No runtime dependencies allowed (types and utils only)"

WHY THIS WORKS:
  - Root handles shared concerns once
  - Each package adds only its specific context
  - No duplication, no contradiction
  - New team members get oriented by reading 2 files

Scenario: Security-Sensitive Project

QUESTION:
  Your project handles payment processing. What configuration
  ensures Claude never accidentally exposes credentials or
  makes unsafe changes to payment code?

STRONG ANSWER:
  CLAUDE.md:
    ## Security Constraints
    - NEVER commit files matching: .env, *.pem, *.key, credentials.*
    - NEVER log or print: API keys, tokens, passwords, card numbers
    - Payment module (src/payments/) is SECURITY-CRITICAL:
      → Always run full test suite after changes
      → Never modify without explicit approval
      → All payment amounts must use Decimal type, never float

    ## Code Review Rules
    - Changes to src/payments/ require 2 reviewers
    - Changes to auth middleware require security team review
    - New dependencies require license check

  .claude/rules/security.md:
    - Run `npm audit` before any dependency changes
    - Check for secrets: `git secrets --scan` before commit
    - All user input must be sanitized before database queries

EXAM SCORING:
  Mention specific file patterns (not just "be careful")
  Reference concrete security practices (Decimal vs float)
  Layer defenses (CLAUDE.md + rules + tooling)

Key Takeaways for the Exam

  1. Know the hierarchy. Enterprise > Project > User > Defaults. More specific wins.
  2. CLAUDE.md is shared via git. Personal preferences go in ~/.claude/rules/.
  3. Be specific and actionable. "Run npm test" beats "make sure tests pass."
  4. Monorepos use subdirectory CLAUDE.md to scope rules per package.
  5. Never put secrets in CLAUDE.md. It's checked into version control.
  6. Review CLAUDE.md quarterly. Stale instructions cause wrong behavior.
CCA exam weight: CLAUDE.md configuration appears in Domain 3 (Configuration & Customization). Expect 3-4 questions on file hierarchy, team setup, and security constraints. This is high-value content — memorize the hierarchy.

Quick Check

1Which configuration file has the highest priority in the CLAUDE.md hierarchy?

The SYSTEM PROMPT is the highest priority and cannot be modified. It defines Claude's core behavior.

2Where should project-specific coding standards and build commands be defined?

CLAUDE.md (PROJECT ROOT) is the primary configuration file for any project and is used to define coding standards, build commands, and other project-specific rules.

3What is the correct use of subdirectory CLAUDE.md files in a monorepo?

Subdirectory CLAUDE.md files are used to define rules specific to a package in a monorepo, adding context without overriding the root file.

4Which of the following should NOT be included in CLAUDE.md (PROJECT ROOT)?

Personal preferences should be included in ~/.claude/rules/*.md, not in CLAUDE.md (PROJECT ROOT), which is for project-specific rules.

5What happens if a subdirectory CLAUDE.md file contains a rule that conflicts with the project root CLAUDE.md?

The project root CLAUDE.md has higher priority and takes precedence over subdirectory rules, even though subdirectory rules can add context.
