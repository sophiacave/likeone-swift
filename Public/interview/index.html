Technical Deep-Dive Questions (Client Round 2)

top 2026 question technical
Q: When would you use RAG vs fine-tuning vs both?
"RAG when you need the model to access current or private data — documents, databases, knowledge bases. The model stays general, and retrieval provides specifics. Fine-tuning when you need the model to behave differently — match a specific tone, follow a format, or learn a domain's reasoning patterns. Both when you need domain behavior AND current data — fine-tune for the reasoning, RAG for the facts. In practice, I reach for RAG first because it's faster to iterate, easier to debug, and you can update the knowledge without retraining. I only fine-tune when RAG alone can't get the behavior right."
Our system: RAG-first with 2,824 vectors. No fine-tuning needed because the retrieval + prompt engineering handles everything.
common technical
Q: What's your chunking strategy for RAG?
"It depends on the document type. For structured data like our brain entries, I chunk by semantic unit — each entry is its own chunk with key, description, and truncated value. For long documents, I use overlapping windows — typically 500-800 tokens with 100 token overlap to maintain context across boundaries. The key insight: chunk size should match your embedding model's sweet spot. mxbai-embed-large handles up to 512 tokens well, so I keep chunks under that. I also store metadata (source, category, timestamp) alongside each chunk for filtering during retrieval."
common technical
Q: How do you evaluate RAG quality?
"Multi-layered. First, retrieval quality — are we finding the right documents? I measure this with similarity scores and manual spot-checks. Second, answer quality — is the generated response faithful to the retrieved context? I built a Truth Engine that cross-references answers against a verified facts database before they're sent. Third, end-to-end testing — I run a megatest suite of known questions and verify the answers are correct. 40 tests, all passing. The goal is catching hallucinations before they reach the user, not after."
Proof: lo-verify CLI, facts.json, megatest (40/40 S+)
advanced technical
Q: What breaks in production AI agent systems?
"Three main failure modes. First, tool call hallucination — the agent invents tool calls that don't exist or passes wrong parameters. I solve this with native function calling (the LLM gets a schema) plus keyword fallback. Second, infinite loops — the agent keeps retrying a failed action. I use max-turn limits and error detection. Third, context poisoning — old bad responses in chat history get repeated. I built an anti-repetition engine that tracks recent responses and blocks overused phrases. The meta-lesson: always have a fallback path and never trust the LLM to self-correct without guardrails."
common technical
Q: Explain the ReAct framework
"ReAct interleaves reasoning with actions in a loop. The agent thinks about what to do, takes an action (like searching or calling a tool), observes the result, then reasons again. This is better than pure chain-of-thought because CoT can hallucinate facts — ReAct grounds reasoning in real tool outputs. Our Telegram bot does this: it reasons about which tool to call (LLM function calling), executes the tool, gets real data, then generates a response grounded in that data. The key is that the action step provides external grounding that prevents the model from making things up."
common technical
Q: How do you approach prompt engineering?
"I treat prompts as code, not magic. Structured system prompts with clear sections: identity, data rules, response format, constraints. I version-control them. For structured outputs, I use JSON schemas and function calling rather than hoping the model formats things correctly. The biggest lesson: be specific about what NOT to do. Anti-instructions ('never invent facts', 'never say you can't if data exists') are often more important than positive instructions."
Proof: Telegram bot system prompt (anti-hallucination rules, response format, data-first policy)
common technical
Q: How do you choose an embedding model?
"Three factors: quality, speed, and dimension size. For our system I use mxbai-embed-large (1024 dimensions) — it's the best quality model that runs locally via Ollama. Higher dimensions capture more nuance but use more storage and compute. For a production system, I'd benchmark 2-3 models on your actual data with a test set of known-relevant pairs. The model that gives the highest retrieval recall on YOUR documents wins — not the one that scores highest on generic benchmarks."
common technical
Q: How do you keep AI system latency low?
"Layer your response times. Fast stuff first: keyword search (instant), vector search (20ms), tool detection (4 seconds with a small model). Then slow stuff in the background: deep reasoning (30 seconds with a large model). Our Telegram bot uses two-phase responses — instant status message ('searching...') then the full answer. Users see immediate feedback. For the retrieval layer specifically, sqlite-vec gives us 20-55ms search across 2,800+ vectors because it runs in-process, no network hop."
hot topic 2026 technical
Q: How do you reduce hallucinations in production?
"Five layers. 1) Source grounding — retrieve verified data BEFORE generating. Never let the model answer from memory alone. 2) Facts database — cross-reference claims against a canonical source of truth. 3) Prompt constraints — explicit anti-hallucination rules: 'only state what appears in the provided context.' 4) Output validation — check generated responses for claims not supported by retrieved context. 5) Monitoring — log and review responses over time, catch patterns. The key principle: the model should be a reasoning engine over YOUR data, not a knowledge source."
Proof: Truth Engine (5 layers), facts.json, anti-hallucination prompt in Telegram
practical technical
Q: How do you manage LLM costs?
"Three strategies. First, use local models for everything that doesn't need frontier-level reasoning — our system runs qwen3 30B locally for most queries, reserving cloud APIs for complex tasks only. Second, smart context management — don't stuff the full database into every prompt. Our agentic query system caps context at 2,000 characters, sending only the most relevant snippets. Third, cache aggressively — if the same question comes up twice, serve from cache rather than re-running the full pipeline. Our entire AI stack runs at $0/month for inference because it's local."
common technical
Q: Compare vector database options — when would you use Pinecone vs Chroma vs something else?
"Pinecone: managed, scales easily, good for teams that don't want to manage infrastructure. Chroma: good for prototyping, easy Python API, but we had reliability issues (data loss). Weaviate/Qdrant: self-hosted, good for companies that need control. pgvector: great if you're already on Postgres. sqlite-vec: what I chose — single file, zero dependencies, runs in-process with sub-100ms latency. The tradeoff is scale: sqlite-vec is perfect up to millions of vectors on a single machine. If you need distributed search across billions of vectors, go Pinecone or Qdrant. For 99% of business use cases, embedded is enough."
